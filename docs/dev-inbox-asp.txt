# Dev Inbox — ASP.NET Core Project Document

## Product Overview
Dev Inbox is a personal engineering workspace that helps a developer triage work from GitHub, Azure DevOps, and private notes in one place. The application is designed around a unified inbox experience: a compact list of things that may need attention, a detail panel for the selected item, and user-owned overlays such as read state, pinning, follow-up, and notes.

The product is intentionally personal. It is not a replacement for GitHub or Azure DevOps, not a workflow engine, not a shared team board, and not a notification delivery platform. Its role is to provide a single daily attention surface over systems that already exist.

This version is designed specifically for an **ASP.NET Core backend** with a simple architecture, low operational complexity, and strong data minimization.

## Product Goals
- Reduce context switching between GitHub, Azure DevOps, and ad hoc personal note-taking.
- Provide a single inbox that answers what deserves attention now.
- Preserve user-owned triage state independently from external tools.
- Keep the backend simple enough to build as a practical .NET learning project.
- Minimize stored third-party data to reduce data leak risk.

## Product Boundaries
### In scope
- Unified inbox list.
- GitHub item ingestion.
- Azure DevOps item ingestion.
- Private notes.
- Personal overlays such as read, saved, pinned, done, tags, priority, and follow-up date.
- Saved views and filters.
- Manual and scheduled synchronization.
- Live detail loading when an inbox item is opened.

### Out of scope
- Team collaboration.
- Shared views.
- Kanban board.
- Write-back to GitHub or Azure DevOps.
- Browser notifications.
- AI summarization.
- Mobile-first UX.
- Replacing the source systems.

## Core UX Model
The main screen uses a three-pane desktop layout:
- left pane for quick views and saved filters;
- center pane for the inbox list and summary counters;
- right pane for item details, overlays, and note interactions.

The center list is the core surface. It should stay fast, compact, and filterable. The right detail panel should open without full navigation and should support lazy loading.

## Architectural Principles
The backend should optimize for simplicity, explicit flow, and low accidental complexity.

### Principles
- Single deployable web application.
- No internal event bus.
- No transactional outbox.
- No CQRS split beyond practical query separation in code.
- No raw archival of third-party item bodies unless explicitly required later.
- OpenAPI-first or OpenAPI-aligned contract generation for the existing frontend.
- External details fetched live when needed instead of copied into the local database.

## High-Level Architecture
The system consists of:
- React frontend, unchanged in overall approach;
- ASP.NET Core Web API backend;
- PostgreSQL database;
- background sync scheduler;
- GitHub REST integration;
- Azure DevOps REST integration.

The backend owns only local application state and lightweight inbox references. Source systems remain the authoritative place for detailed PR or work item content.

## Backend Shape
The backend is a simple modular-by-folder application, not a strict modular monolith. A practical project structure could look like this:

```text
backend/
  DevInbox.Web/
    Features/
      Inbox/
```

This structure keeps feature ownership visible without introducing complex inter-module rules.

## Functional Areas
### Inbox
Responsible for:
- listing inbox items;
- filtering and sorting;
- summary counters;
- loading a selected item detail by delegating to the proper integration service;
- updating local item state.

### GitHub integration
Responsible for:
- reading GitHub user configuration;
- calling GitHub APIs during sync;
- mapping lightweight GitHub metadata into local inbox records;
- loading live detail for a selected GitHub item.

### Azure DevOps integration
Responsible for:
- reading Azure DevOps configuration;
- calling Azure DevOps APIs during sync;
- mapping lightweight ADO metadata into local inbox records;
- loading live detail for a selected ADO item.

### Notes
Responsible for:
- creating and editing private notes;
- linking notes to inbox items;
- storing user-authored note content.

### Settings
Responsible for:
- GitHub PAT;
- Azure DevOps PAT;
- watched repositories or projects;
- sync preferences.

### Saved Views
Responsible for persisting named filter presets used by the inbox UI.

### Sync
Responsible for:
- scheduled background sync;
- manual sync trigger;
- per-source checkpoint tracking;
- retry and failure logging.

## Data Protection Model
A central design requirement is **data minimization**.

### Objective
The application should persist only the minimum amount of external data needed to render the inbox, preserve user triage state, and later re-fetch the correct source item.

### Persisted external fields
For GitHub and Azure DevOps sourced items, the database may store:
- source type;
- external id;
- external number or key;
- repository identifier or project identifier;
- item classification;
- status/reason classification used for inbox grouping;
- URL to source item if useful;
- timestamps for activity and sync;
- local visibility flags such as active or archived.

### Non-persisted external content
The database should avoid storing:
- PR body text;
- PR review text;
- comment bodies;
- mention thread content;
- ADO work item title and description if not strictly necessary for list rendering;
- copied acceptance criteria;
- copied discussion content;
- user names or rich profile details unless operationally required.

### Persisted local data
The application should persist:
- unread or read state;
- saved, pinned, done, snoozed flags;
- tags;
- priority;
- follow-up date;
- private notes;
- saved views;
- settings and credentials.

### Detail loading rule
When a user opens an item, the backend should fetch fresh details from GitHub or Azure DevOps and return them to the frontend without persisting the external payload. Local notes and local state are merged into the response at runtime.

## Data Model
A simple database model is enough.

| Table | Purpose |
|---|---|
| `users` | Local application user. |
| `user_settings` | Per-user configuration, encrypted PATs, watched repos/projects, sync interval. |
| `inbox_items` | Lightweight persisted references to GitHub and ADO items. |
| `inbox_item_states` | User-owned triage state for each inbox item. |
| `notes` | Private note content written inside Dev Inbox. |
| `note_links` | Links between notes and inbox items or external references. |
| `saved_views` | Named filter presets. |
| `sync_checkpoints` | Last successful sync markers by user and source. |
| `sync_runs` | Operational history of sync executions. |

## Synchronization Strategy
Sync should be simple and deterministic.

### Schedule
A hosted background service runs every few minutes, or on a user-defined interval, and executes per-source sync for the current user or configured users.

### GitHub sync
The GitHub sync process should:
1. load user settings and watched repositories;
2. fetch only the item categories needed for the inbox;
3. map each relevant item into a lightweight inbox reference;
4. upsert records into `inbox_items`;
5. preserve user-owned state in `inbox_item_states`;
6. update the sync checkpoint.

### Azure DevOps sync
The Azure DevOps sync process should follow the same model:
1. load settings;
2. query assigned or followed items;
3. capture lightweight metadata only;
4. upsert inbox references;
5. update checkpoints.

### No raw import tables
There are no raw staging tables such as `github_pull_requests` or `ado_work_items`. The sync process writes directly into lightweight inbox references because the product only needs list-level data locally.

## Detail Retrieval Strategy
Detail retrieval is live and on-demand.

### Request flow
1. User clicks an inbox row.
2. Frontend calls the detail endpoint.
3. Backend reads the local inbox reference.
4. Backend decides which integration client to call.
5. Backend fetches full source detail from GitHub or Azure DevOps.
6. Backend merges local state and notes.
7. Backend returns one DTO to the frontend.
8. External detail payload is not persisted.

### Benefits
- lower local data sensitivity;
- fresher details;
- simpler storage model;
- fewer schema concerns for third-party payloads.

### Trade-off
The detail panel may be slower than the list because it depends on a live external call. The frontend should therefore use loading placeholders and error states.

## API Design
The frontend remains the same in architectural style, so the backend should continue exposing a typed OpenAPI contract.

### Suggested endpoints
#### Inbox
- `GET /api/inbox`
- `GET /api/inbox/summary`
- `GET /api/inbox/items/{id}`
- `PATCH /api/inbox/items/{id}/state`

#### Notes
- `GET /api/notes`
- `POST /api/notes`
- `PUT /api/notes/{id}`
- `DELETE /api/notes/{id}`
- `POST /api/notes/{id}/links`

#### Saved views
- `GET /api/saved-views`
- `POST /api/saved-views`
- `PUT /api/saved-views/{id}`
- `DELETE /api/saved-views/{id}`

#### Settings
- `GET /api/settings`
- `PUT /api/settings`

#### Sync
- `POST /api/sync/run`
- `GET /api/sync/status`

## Frontend Compatibility
The frontend remains aligned with the current product direction:
- React + TypeScript;
- Vite;
- TanStack Query for server state;
- Zustand for local UI state;
- generated TypeScript client;
- feature-based frontend organization.

Required frontend behavior for this backend:
- list queries should be local-database fast;
- detail panel should load on demand;
- state mutations should update immediately in UI;
- list filters should remain URL-driven;
- detail query caching should be short-lived and memory-based.

## Security Approach
### Credential handling
- PATs must be encrypted at rest.
- Settings endpoints must avoid echoing secrets back to the UI.
- Secret rotation should be supported by updating settings.

### Logging
- Avoid logging response payloads from GitHub or Azure DevOps.
- Avoid logging note bodies in structured logs.
- Log sync counts, timings, and failures, but not sensitive source content.

### Access model
- Personal single-user or very small internal usage.
- No public multi-tenant exposure.
- No shared note visibility between users in the base design.

## Suggested Technology Stack
- ASP.NET Core Web API

- Swashbuckle or NSwag for OpenAPI

## Testing Strategy
### Backend tests
- unit tests for sync mapping and state updates;
- integration tests for persistence and endpoint behavior;
- API contract smoke tests;
- sync tests against mocked GitHub and ADO responses.

### Frontend contract safety
The generated TypeScript client should be regenerated from the backend OpenAPI definition so the frontend remains aligned with the API surface.

## Delivery Scope for MVP
The MVP is complete when:
1. GitHub inbox items appear in the unified list.
2. Azure DevOps inbox items appear in the unified list.
3. Notes can be created and linked.
4. Read, saved, pinned, done, and follow-up states persist.
5. Saved views work.
6. The detail panel loads current source data on demand.
7. Manual and scheduled sync both work.
8. No unnecessary third-party body content is stored in the database.

## Non-Goals for the Backend
This backend deliberately does not attempt to be:
- a domain-driven architecture showcase;
- a message-driven system;
- an event-sourced design;
- a multi-tenant SaaS platform;
- a replication store of GitHub or Azure DevOps data.

Its value is practical: one clean .NET service that keeps a local attention layer and retrieves full source details only when needed.

## Recommended Implementation Order
1. Create database schema and EF Core migrations.
2. Build settings management and secret storage.
3. Implement inbox list and state update endpoints.
4. Implement GitHub sync.
5. Implement GitHub live detail endpoint.
6. Implement Azure DevOps sync.
7. Implement Azure DevOps live detail endpoint.
8. Implement notes and saved views.
9. Add scheduled sync, logging, and operational polish.

## Summary
Dev Inbox in this form is a lightweight ASP.NET Core service centered on a local inbox index, local user triage state, and live source detail retrieval. The design deliberately favors simplicity, privacy, and learnability over advanced internal architecture.
