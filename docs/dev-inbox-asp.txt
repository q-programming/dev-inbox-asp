## Dev Inbox — ASP.NET Core Project Document

### Product Overview

Dev Inbox is a personal engineering workspace that helps a developer triage work from GitHub, Azure DevOps, and private notes in one place. The application is designed around a unified inbox experience: a compact list of things that may need attention, a detail panel for the selected item, and user-owned overlays such as read state, pinning, follow-up, priority, tags and notes.

The product is intentionally personal. It is not a replacement for GitHub or Azure DevOps, not a workflow engine, not a shared team board, and not a notification delivery platform. Its role is to provide a single daily attention surface over systems that already exist.

This version is designed specifically for an **ASP.NET Core backend** with a simple architecture, low operational complexity, and strong data minimization.

---

### Product Goals

- Reduce context switching between GitHub, Azure DevOps, and personal note-taking.
- Provide a single inbox that answers what deserves attention now.
- Preserve user-owned triage state independently from external tools.
- Keep the backend simple enough to build as a practical .NET learning project.
- Minimize stored third-party data to reduce data leak risk.

### Core UX Model

The main screen uses a three-pane desktop layout:

- left pane for quick views and saved filters;
- center pane for the inbox list and summary counters;
- right pane for item details, overlays, and note interactions.

The center list is the core surface. It should stay fast, compact, and filterable. The right detail panel should open without full navigation and should support lazy loading.

### Architectural Principles

The backend optimizes for simplicity, explicit flow, and low accidental complexity.

#### Principles

- Single deployable web application.
- Feature-sliced modular structure.
- Lightweight event-driven communication between modules.
- No MediatR.
- No Kafka, RabbitMQ, MassTransit or external broker for MVP.
- No transactional outbox for MVP.
- No CQRS split beyond practical query separation in code.
- No raw archival of third-party item bodies unless explicitly required later.
- OpenAPI-first or OpenAPI-aligned contract generation for the existing frontend.
- External details fetched live when needed instead of copied into the local database.

---

### Module Communication

Features communicate primarily through lightweight in-process events.

The application uses a custom event infrastructure instead of MediatR or external messaging platforms.

Core contracts:

- `IEvent`
- `IEventHandler<T>`
- `IPublisher`

This keeps module boundaries explicit while avoiding heavier mediator frameworks.

Examples:

```text
Identity -> UserAuthenticatedEvent
GitHub   -> PullRequestImportedEvent
ADO      -> WorkItemImportedEvent
Notes    -> NoteCreatedEvent
```

Audit subscribes to relevant events and records activity.

Preferred:

```text
Feature -> Event -> Feature
```

Avoid:

```text
Feature -> Service -> Service -> Service
```

The goal is low coupling and simple evolution of feature boundaries.

---

### Event Publisher

The platform provides a lightweight event publisher supporting two execution modes.

#### `Publish(...)`

- synchronous
- caller waits for all handlers
- handlers execute sequentially
- exceptions propagate to the caller
- intended for consistency-sensitive workflows

#### `PublishAsync(...)`

- fire-and-forget
- handlers execute independently
- each handler receives a dedicated DI scope
- failures are isolated and logged
- intended for background workflows

Examples:

```text
UserAuthenticatedEvent -> PublishAsync()
SettingsUpdatedEvent   -> Publish()
ApplicationStartedEvent -> PublishAsync()
```

This model intentionally favors simplicity over framework abstraction and replaces the need for MediatR in the current scope.

### High-Level Architecture

The system consists of:

- React frontend;
- ASP.NET Core Web API backend;
- PostgreSQL database;
- background sync scheduler;
- GitHub REST integration;
- Azure DevOps REST integration;
- custom in-process event publisher.

The backend owns only local application state and lightweight inbox references. Source systems remain authoritative for detailed PR or work item content.

### Functional Areas

#### Identity

Responsible for:

- user authentication;
- local user account state;
- login/logout flows;
- publishing user-related events such as `UserAuthenticatedEvent`.

#### Inbox

Responsible for:

- listing inbox items;
- filtering and sorting;
- summary counters;
- loading a selected item detail by delegating to the proper integration service;
- updating local item state.

#### GitHub integration

Responsible for:

- reading GitHub user configuration;
- calling GitHub APIs during sync;
- mapping lightweight GitHub metadata into local inbox records;
- loading live detail for a selected GitHub item;
- reacting to relevant events such as login or manual sync.

#### Azure DevOps integration

Responsible for:

- reading Azure DevOps configuration;
- calling Azure DevOps APIs during sync;
- mapping lightweight ADO metadata into local inbox records;
- loading live detail for a selected ADO item;
- reacting to relevant events such as login or manual sync.

#### Notes

Responsible for:

- creating and editing private notes;
- linking notes to inbox items;
- storing user-authored note content;
- publishing note-related events when needed.

#### Settings

Responsible for:

- GitHub PAT;
- Azure DevOps PAT;
- watched repositories or projects;
- sync preferences;
- publishing settings-related events when settings change.

#### Saved Views

Responsible for persisting named filter presets used by the inbox UI.

#### Audit

Responsible for:

- storing audit entries;
- listening to audit-worthy events;
- recording user activity and system activity;
- avoiding storage of sensitive payloads such as PATs or external API response bodies.

#### Sync

Responsible for:

- scheduled background sync;
- manual sync trigger;
- per-source checkpoint tracking;
- retry and failure logging;
- publishing or handling sync-related events.

### Data Protection Model

A central design requirement is **data minimization**.

#### Objective

The application should persist only the minimum amount of external data needed to render the inbox, preserve user triage state, and later re-fetch the correct source item.

#### Persisted external fields

For GitHub and Azure DevOps sourced items, the database may store:

- source type;
- external id;
- external number or key;
- repository identifier or project identifier;
- item classification;
- status/reason classification used for inbox grouping;
- URL to source item if useful;
- timestamps for activity and sync;
- local visibility flags such as active or archived.

#### Non-persisted external content

The database should avoid storing:

- PR body text;
- PR review text;
- comment bodies;
- mention thread content;
- ADO work item title and description if not strictly necessary for list rendering;
- copied acceptance criteria;
- copied discussion content;
- user names or rich profile details unless operationally required.

#### Persisted local data

The application should persist:

- unread or read state;
- saved, pinned, done, snoozed flags;
- tags;
- priority;
- follow-up date;
- private notes;
- saved views;
- settings and credentials;
- audit entries;
- sync checkpoints and sync run history.

#### Detail loading rule

When a user opens an item, the backend should fetch fresh details from GitHub or Azure DevOps and return them to the frontend without persisting the external payload. Local notes and local state are merged into the response at runtime.

### Synchronization Strategy

Sync should be simple and deterministic.

#### Schedule

A hosted background service runs every few minutes, or on a user-defined interval, and executes per-source sync for configured users.

#### GitHub sync

The GitHub sync process should:

- load user settings and watched repositories;
- fetch only the item categories needed for the inbox;
- map each relevant item into a lightweight inbox reference;
- upsert records into `inbox_items`;
- preserve user-owned state in `inbox_item_states`;
- update the sync checkpoint.

#### Azure DevOps sync

The Azure DevOps sync process should follow the same model:

- load settings;
- query assigned or followed items;
- capture lightweight metadata only;
- upsert inbox references;
- update checkpoints.

#### Login-triggered sync

A successful authentication event may trigger GitHub or Azure DevOps refresh work using `PublishAsync(...)` so the user is not blocked by synchronization.

#### No raw import tables

There are no raw staging tables such as `github_pull_requests` or `ado_work_items`. The sync process writes directly into lightweight inbox references because the product only needs list-level data locally.

---

### Detail Retrieval Strategy

Detail retrieval is live and on-demand.

#### Request flow

- User clicks an inbox row.
- Frontend calls the detail endpoint.
- Backend reads the local inbox reference.
- Backend decides which integration client to call.
- Backend fetches full source detail from GitHub or Azure DevOps.
- Backend merges local state and notes.
- Backend returns one DTO to the frontend.
- External detail payload is not persisted.

#### Benefits

- lower local data sensitivity;
- fresher details;
- simpler storage model;
- fewer schema concerns for third-party payloads.

#### Trade-off

The detail panel may be slower than the list because it depends on a live external call. The frontend should therefore use loading placeholders and error states.

### Security Approach

#### Credential handling

- PATs must be encrypted at rest.
- Settings endpoints must avoid echoing secrets back to the UI.
- Secret rotation should be supported by updating settings.

#### Logging

- Avoid logging response payloads from GitHub or Azure DevOps.
- Avoid logging note bodies in structured logs.
- Avoid logging PATs, OAuth tokens, authorization headers or credentials.
- Log sync counts, timings and failures, but not sensitive source content.

#### Access model

- Personal single-user or very small internal usage.
- No public multi-tenant exposure.
- No shared note visibility between users in the base design.

### Testing Strategy

#### Backend tests

- unit tests for event publishing behavior;
- unit tests for sync mapping and state updates;
- integration tests for persistence and endpoints;
- API contract smoke tests;
- sync tests against mocked GitHub and ADO responses.

#### Event publisher tests

The event infrastructure should be tested as an independent component:

- `Publish(...)` executes registered handlers;
- `Publish(...)` executes handlers sequentially;
- `Publish(...)` propagates exceptions;
- `PublishAsync(...)` returns immediately;
- `PublishAsync(...)` executes all handlers;
- `PublishAsync(...)` isolates handler failures;
- async handlers receive valid scoped dependencies.

#### Frontend contract safety

The generated TypeScript client should be regenerated from the backend OpenAPI definition so the frontend remains aligned with the API surface.

### Delivery Scope for MVP

The MVP is complete when:

- GitHub inbox items appear in the unified list.
- Azure DevOps inbox items appear in the unified list.
- Notes can be created and linked.
- Read, saved, pinned, done, and follow-up states persist.
- Saved views work.
- The detail panel loads current source data on demand.
- Manual and scheduled sync both work.
- Audit records important user and system activity.
- No unnecessary third-party body content is stored in the database.

---

### Non-Goals for the Backend

This backend deliberately does not attempt to be:

- a domain-driven architecture showcase;
- a message-driven distributed system;
- an event-sourced design;
- a multi-tenant SaaS platform;
- a replication store of GitHub or Azure DevOps data.

Its value is practical: one clean .NET service that keeps a local attention layer and retrieves full source details only when needed.

### Summary

Dev Inbox in this form is a lightweight ASP.NET Core service centered on a local inbox index, local user triage state, live source detail retrieval, and simple event-driven communication between feature modules. The design deliberately favors simplicity, privacy, and learnability over advanced internal architecture.
