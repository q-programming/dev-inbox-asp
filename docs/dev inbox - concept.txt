# Dev Inbox — Project Document
## Overview
Dev Inbox is a personal engineering workspace application designed to aggregate and triage a developer's daily work context in one place. The core problem it solves is fragmentation: GitHub pull requests live in one tab, Azure DevOps work items in another, personal notes scattered across sticky notes, Notepad and browser bookmarks. Dev Inbox pulls all of this into a unified, filterable inbox, giving the developer a single answer to the question: **"What do I need to focus on today?"**

The application is also a learning project, built deliberately to explore modern Java backend patterns — Spring Modulith, domain events, transactional outbox, virtual threads — and a well-structured React frontend with TanStack Query, Zustand, and a generated TypeScript API client.

***
## Business Goals
- Reduce cognitive load caused by switching between GitHub, Azure DevOps, email and personal notes during a working day.
- Provide a personal "attention layer" on top of existing team tools, without replacing them.
- Give the developer instant visibility into: what needs review, what was just mentioned or commented on, what ADO work items are assigned or followed, and any personal notes linked to those items.
- Be a product the developer actually opens every morning and keeps open all day.

***
## What It Is NOT
- Not a replacement for GitHub, Azure Boards, Jira or any other team tool.
- Not a project management or Kanban board.
- Not a team collaboration tool — this is personal, per-user, not shared.
- Not a notification relay or email client.
- Not a monitoring/observability dashboard.

***
## Key Features (MVP Scope)
### Unified Inbox
A single, filterable list of items from all sources. Each item is derived from one of three sources: GitHub, Azure DevOps, or a personal local note. The inbox is the central UI and the primary use case.
### GitHub Items
- Pull requests authored by the user (own PRs)
- Pull requests awaiting user's review (review requests)
- Comments and threads where the user was @mentioned
- PR status updates (new review, approved, changes requested)

Items are imported via GitHub REST API and synchronized incrementally on a schedule.[^1][^2]
### Azure DevOps Items
- Work items assigned to the user
- Work items followed by the user
- Recent activity on followed items

Items are imported via Azure DevOps REST API and synchronized incrementally.[^3][^4]
### Personal Notes
- Lightweight freeform notes
- Can be attached to a GitHub PR or ADO work item, or standalone
- Support tags and optional follow-up date
### Item Enrichment
Every inbox item, regardless of source, supports:
- Personal priority: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`
- Personal status: `UNREAD`, `SAVED`, `DONE`, `PINNED`, `SNOOZED`
- Tags (user-defined strings)
- Private note (freeform text, markdown)
- Follow-up date

These personal overlays are stored separately from the source data and are never written back to GitHub or Azure DevOps.
### Filtering and Saved Views
The inbox list supports persistent filtering by:
- Source: GitHub / ADO / Notes
- Item type: review request, mention, own PR, assigned, followed, note
- Status: unread, saved, done, pinned
- Age: today, last 3 days, stale (>7 days)
- Repository or project
- Tags

Users can save named filter combinations as custom views (e.g., "Review queue", "My ADO today", "Mentions to follow up"). GitHub itself encourages filter-based inbox triage workflows, and the same model applies here.[^5][^6]
### Connection Settings
User can configure:
- GitHub personal access token (PAT) and list of watched repositories
- Azure DevOps organization, project, and PAT
- Sync interval preference

## Backend Architecture
### Spring Modulith
The backend is structured as a **modular monolith** using Spring Modulith. Each module is a top-level Java package with strict boundary enforcement. Cross-module communication happens exclusively through domain events, never by direct bean injection from another module's internal types.[^10][^11]

Modulith enforces this with `ModularityTests`, which verify at build time that no module imports internal types from another module. ArchUnit is added as an additional layer for custom architectural rules.[^12][^11]
### Modules
| Module | Responsibility |
|---|---|
| `identity` | User entity, authentication context, per-user integration credentials (GitHub PAT, ADO PAT/org) |
| `github-integration` | GitHub API client, PR import, mention import, incremental sync per user |
| `ado-integration` | Azure DevOps API client, work item import, incremental sync per user |
| `inbox` | Read model (inbox projection), query service, REST endpoints for frontend. Listens to events from integration modules |
| `notes` | Personal notes CRUD, note-to-item linking |
| `sync` | Scheduler triggering incremental sync jobs across integration modules |
| `shared` | Shared value objects, events, utility types — no business logic |
### Domain Events & Transactional Outbox
Integration modules publish domain events (`PullRequestSyncedEvent`, `WorkItemSyncedEvent`, `NoteSavedEvent`) using Spring Modulith's event publication registry, which provides transactional outbox semantics out of the box. Events are written atomically with the data in the same database transaction and processed asynchronously by the inbox module to update the read model.[^10][^11]

This pattern prevents the classic dual-write problem (data saved but event not published, or vice versa). For a sync-heavy application like this, it ensures that the inbox projection stays consistent even if the application restarts mid-sync.[^13][^14]
### Inbox as Read Model
The `inbox` module maintains a separate `inbox_projection` table, which is the pre-aggregated, denormalized view of all item types optimized for the list query. This is a lightweight CQRS approach applied only where it adds value: the inbox list query has different requirements (filtering, sorting, pagination by many dimensions) than the write side (upserting sync data).[^13][^10]

The projection contains: `id`, `user_id`, `source_type`, `item_type`, `source_id`, `title`, `subtitle`, `repository`, `reason`, `is_unread`, `is_saved`, `is_done`, `is_pinned`, `priority`, `tags`, `last_activity_at`, `synced_at`, `private_note`, `follow_up_at`.
### Virtual Threads
GitHub and ADO sync jobs involve sequential I/O-bound calls (list PRs → fetch details per PR). These run on virtual threads introduced in Java 21, eliminating the need for reactive programming while still achieving good concurrency for multiple per-user sync tasks. Spring Boot's `spring.threads.virtual.enabled=true` enables this globally.[^15]
### Observability
- **Micrometer** for application metrics (sync job durations, inbox projection lag, API response times).
- **Spring Boot Actuator** for health and readiness endpoints.
- **OpenTelemetry OTLP export** for distributed traces. Pairs with Grafana/Tempo locally via Docker Compose.[^16][^17]
- **Spring Modulith Insight** for module interaction visibility during development.[^18][^19]
### OpenAPI Contract
Springdoc-openapi generates the OpenAPI spec from controllers and DTOs. A Maven profile `generate-client` runs during `mvn compile`, starts the app, dumps the spec, and invokes the TypeScript client generator. The generated client is output directly to the frontend project's `generated/api-client/` folder and is excluded from Git.[^20][^21]

### Feature-Based Structure
The frontend is organized by feature, not by technical type:[^27]

```
frontend/
  src/
    features/
      inbox/
        components/
        hooks/
        types/
      review-requests/
      mentions/
      ado-items/
      notes/
      saved-views/
      settings/
    shared/
      api/          ← facade over generated API client
      ui/           ← design system components
      hooks/
      utils/
    app/
      router/
      shell/
  generated/
    api-client/     ← Git-ignored, regenerated on mvn compile
```
### API Client Layer
The generated TypeScript client lives in `generated/api-client/` and is referenced via a Vite/tsconfig path alias `@api`. Frontend code never imports directly from the generated client. Instead, `src/shared/api/` exports typed wrapper functions that map API DTOs to UI-specific view models.[^28][^29]
### Server State vs UI State
- **TanStack Query** owns everything that comes from the server: inbox list, detail fetch, notes list, settings. Query keys are derived from URL parameters so filter state changes invalidate cache correctly.[^22]
- **Zustand** is used only for pure UI state that has no server representation: which item is selected, whether detail panel is open, command palette open/close, density preference.[^23][^30]
### URL-Driven Filters
All active filters are encoded in URL query parameters. This makes views bookmarkable, shareable, and browser-navigable. TanStack Query keys include the filter params, so changing a filter triggers an automatic refetch or cache hit.[^27]
### Keyboard Navigation
The inbox supports keyboard-first operation — an important consideration for a tool built for developers:
- `j` / `k` — navigate items
- `Enter` — open detail panel
- `s` — save/unsave item
- `d` — mark done
- `p` — pin
- `n` — add note
- `Cmd/Ctrl + K` — open command palette

## Sync Strategy
Each integration module maintains a `last_synced_at` timestamp per user per source. Sync jobs run on a configurable schedule (default: every 5 minutes) and fetch only items updated since the last sync timestamp. On first sync, a configurable lookback window is used (default: 30 days).

GitHub sync fetches:
- Open PRs authored by user, across configured repositories
- Review requests assigned to user
- Notifications filtered by `reason=mention` and `reason=review_requested`[^1][^2]

Azure DevOps sync fetches:
- Work items where `Assigned To = @Me`
- Work items in the user's followed list
- Recent updates on followed items[^3][^4]

***
## Security Assumptions
- Single-user or small-team internal application, not a public SaaS.
- Authentication via session cookie or JWT (Spring Security).
- Integration credentials (GitHub PAT, ADO PAT) stored encrypted at rest per user.
- No OAuth flows in MVP — personal access tokens only.
- No public exposure — runs locally or on an internal server.

***
## Out of Scope (MVP)
The following features are explicitly deferred and should **not** be designed into the MVP schema or UI:

- Kanban or board view
- Team/multi-user shared views
- Write-back to GitHub or ADO (no creating PRs, comments, work items)
- Build/pipeline integration (schema placeholder only)
- Copilot CLI usage tracking
- AI-powered summaries or suggestions
- Mobile responsive layout (desktop-first only)
- Push notifications or browser notifications
- Rich text editor for notes

***
## Future Considerations
These are tracked as intentional future extensions, not hidden scope:

- **Build/CI widget** — placeholder exists in the data model (`source_type: BUILD`), implementation deferred
- **Copilot CLI usage module** — separate adapter reading from GitHub org-level Copilot metrics API, or local session stats via `/context` command[^34][^35]
- **AI daily summary** — "What needs my attention today?" generated from inbox state
- **Command palette AI** — natural language filter ("show stale reviews older than 3 days")
- **Team view** — aggregate inbox view for a team lead, read-only

***
## Definition of Done (MVP)
The MVP is considered complete when:

1. GitHub PR import works: own PRs, review requests, and @mentions appear in inbox.
2. Azure DevOps work item import works: assigned and followed items appear.
3. Inbox list renders with filtering by source, type, and status.
4. Per-item overlays work: save, pin, done, private note, tags.
5. Saved views can be created and recalled.
6. Detail panel shows full item metadata and linked entities.
7. Notes can be created standalone and linked to a PR or ADO item.
8. Sync runs on schedule and updates the projection.
9. App starts with a single `make dev` command.
10. Backend integration tests pass with Testcontainers.
11. Frontend component tests cover inbox list, filters, and detail panel.
